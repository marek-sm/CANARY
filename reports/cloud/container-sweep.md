# Can the sweep run in a pinned image, with tools still sandboxed?

- Branch: `cloud/container-sweep`, from `origin/main` at `3b165bf` (#64 merged). Final prototype commit for the runs below: `ba0cc75`.
- Date: 2026-11-04. Cloud VM: Ubuntu 24.04.5, x86_64, 4 CPUs, 15 GB, running as root. Kernel `6.18.44-fc-v230`, then `6.18.44-fc-v233` after the VM restarted mid-session. Docker Engine 29.9.2 with the containerd image store, the `runc` runtime, cgroup v1, the builtin seccomp profile, and no AppArmor or SELinux.
- Status: a **prototype for a decision the project lead hasn't made**. Decision 0025 item 12 still governs: the official sweep runs on the host with a null `container_digest`. Nothing on `main` calls this code, and nothing here changes `SPEC.md`, decisions, `TASKS.md`, `STATUS.md`, locked schemas, or hash pins.
- Who reviewed it: an AI session wrote and ran it. That's no substitute for the human reviewer `SPEC.md` requires, and this report doesn't claim one.
- Provider calls: none. Only the mock provider ran, and no key was created or used. `runner/paid_run.py`'s refusals are unchanged. The network probe made two bare TCP connections to `api.anthropic.com:443`, sending no TLS and no bytes. The key file in the probe held a fake value.
- Evaluation candidates: not touched. Nothing read `corpus/evaluation/`, and #73's branch wasn't fetched. Every run used `corpus/development`.

## Answer

**Yes, on this Linux/amd64 host.** The full mock grid ran inside a pinned, non-root (uid 10001), read-only-root image, with `bwrap` and `tools/no_exec.py` confining every tool. It ran 90 of 90 trials and verified complete. Its outcomes are identical to the host run's, by a hash over every trial's status, security and utility facts, and tool facts. `python -m runner.paid_run record` then wrote a valid record from it in a scratch copy, and `check` passed in the same image.

It takes **two loosening `docker run` options and no `--privileged`**:

1. `--security-opt seccomp=docker/sweep/seccomp-bwrap.json`: Docker's default profile plus five measured additions. `seccomp=unconfined` isn't needed.
2. `--security-opt systempaths=unconfined`. No narrower Docker option does the same job.

Every other option tightens.

Four things don't work, or aren't proven yet:

- **The paid-run gate can't see the image.** The record schema has `additionalProperties: false` and no container field, so a record made in one image lets `check` pass in another. Closing that is a schema change, which is the lead's call (finding 1).
- **The runner's network.** Docker can't give the outer runner only `api.anthropic.com`. With `--network bridge` the runner reached an arbitrary host. The tools still had no network at all (finding 4).
- **A Mac on arm64.** Nothing here ran on arm64 or on Docker Desktop. Its digest would differ from the one below, and its kernel and VM are untested (see "Apple Silicon").
- **The canonical build.** `Dockerfile.sweep`'s default build path (Debian snapshot packages, the ghcr.io uv image, Docker Hub bases) couldn't be built here. This VM's egress policy blocks Debian mirrors and ghcr.io blobs, and Docker Hub returned 429. The image I measured used the Ubuntu-sourced variant described below. **The canonical image's digest is unknown.**

## The smallest `docker run` option set

This is the set `docker/sweep/launch.py` uses:

| Option | Effect | What it loosens or tightens |
|---|---|---|
| `--security-opt seccomp=docker/sweep/seccomp-bwrap.json` | Loosens | Docker's default profile (moby `profiles/seccomp/default.json`, SHA-256 `6416b477…3053f6`, fetched 2026-11-04), plus five additions generated by `docker/sweep/make_seccomp.py` (output SHA-256 `25510237…683d06`). They apply to **every process in the container**, the outer runner included: (1) `clone` when the flags hold all seven namespace bits (`CLONE_NEWNS`, `NEWCGROUP`, `NEWUTS`, `NEWIPC`, `NEWUSER`, `NEWPID`, `NEWNET`); a clone with none of them was already allowed, and any other mix stays denied. (2) `unshare` with `CLONE_NEWUSER` and no other namespace bit. (3) `mount`, (4) `umount2`, and (5) `pivot_root` with no argument filter. Still denied: `setns`, `clone3` with namespaces (ENOSYS, so glibc falls back to `clone`), the new mount API (`fsopen`, `fsmount`, `open_tree`, `move_mount`, `mount_setattr`), `chroot`, `sethostname`, `bpf`, `perf_event_open`, and every other default denial. With `--cap-drop ALL`, a mount can only succeed inside a user namespace the process just made, so it can't change the container's own mount tree. The new surface is the kernel's user-namespace and mount code, which unprivileged processes on a stock Ubuntu host already reach |
| `--security-opt systempaths=unconfined` | Loosens | Docker stops bind-masking `/proc/kcore`, `/proc/keys`, `/proc/timer_list`, `/proc/sched_debug`, `/proc/acpi`, `/proc/scsi`, `/sys/firmware`, and similar paths, and stops remounting `/proc/sys`, `/proc/sysrq-trigger`, `/proc/irq`, and `/proc/bus` read-only. The kernel refuses a fresh procfs (bwrap's `--proc /proc`) in a user namespace while those overmounts hide parts of the container's `/proc` ("Can't mount proc on /newroot/proc: Operation not permitted"). The container runs as uid 10001 with no capabilities, so writes to `/proc/sys` and reads of `/proc/kcore` are still refused by ordinary permission checks. What it does expose is the read-only information leaks those masks hide (for example `/proc/timer_list` and `/proc/sched_debug`) to the outer runner. Inside bwrap a tool sees only its own fresh `/proc` (one PID; see the probe) |
| `--user 10001:10001` | Tightens | Non-root, the uid `Dockerfile` already uses |
| `--cap-drop ALL` | Tightens | No capabilities, even in the container's root user namespace |
| `--security-opt no-new-privileges` | Tightens | No setuid gain. bwrap here isn't setuid, so it works |
| `--read-only` | Tightens | The image's root filesystem is read-only |
| `--tmpfs /tmp:rw,nosuid,nodev,noexec,size=256m` | Tightens | The only scratch space, and nothing in it can execute |
| `--pids-limit 512` | Tightens | Bounds runaway forks |
| `--network none` (default) or `bridge` (paid runs only) | Tightens, or loosens for paid runs | Finding 4 |
| `--mount …,dst=/app,readonly` | Tightens | The checkout, read-only. The runner can't change hashed code |
| `--mount …,dst=/results` | Allows | Results are the only writable bind |
| `--mount …,dst=/run/canary,readonly` | Allows | The launcher's container file |

## Findings, ranked

Ranked first by whether they could change a reported number, then by whether they could break a safety boundary. A tag like "(container)" marks a finding that exists only in the container; "(host too)" marks one that exists on the host as well.

### Could change a reported number

1. **The paid-run gate doesn't bind the installed environment, and with no container field it can't bind the image (host too, container).**
   - Where: `runner/paid_run.py:129` (`paid_run_refusal`); `schemas/paid_run_record.schema.json:7` (`additionalProperties: false`, no container field).
   - Repro:
     - Build `canary-sweep:drift` = `canary-sweep:proto` with `jsonschema` 4.21.0 written over the venv (`uv.lock` pins 4.26.0; `validators.py` SHA-256 `c93da801…` vs `97f171b9…`).
     - The sandbox fingerprint is unchanged: `linux-bwrap:tool-sandbox-v0.3.0:7b60c4fb0074ea5a`.
     - Copy a record made in `canary-sweep:proto` into the scratch checkout.
     - `launch.py --image canary-sweep:drift … -- python -m runner.paid_run check` prints "paid runs may start here".
   - Why it matters: `code_sha256` covers `uv.lock`, but nothing checks that the installed packages match it. On the host the `.venv` has the same gap. That includes the provider SDK a paid cell calls and the `jsonschema` that verify uses.
   - What the prototype closes: the record step. `_check_preflight` now refuses a mock grid whose provenance names another image, or none (`runner/paid_run.py:198`; repros (b) and (c) under "container_digest").
   - What stays open: the paid-call gate itself, until the record schema gains a container field.

2. **A sandbox that can't start still reads as available, and `verify` reports a grid of failures as complete (container, and host too wherever bwrap can't create namespaces, such as Ubuntu 23.10+ without the sysctl).**
   - Where: `tools/sandbox.py:166`/`:175` (`mode()` checks only that `bwrap` is on `PATH`); `runner/grid_dev.py:256` (`complete` counts trials, not statuses); `runner/execute.py:763` (the launch failure becomes `infrastructure_failure`).

     - Every trial still records `tool_sandbox` `linux-bwrap:…:7b60c4fb…`.

3. **The sandbox fingerprint differs between host and container (container).**

### Could break a safety boundary

4. **The runner's network can't be limited to the provider (container).**
   - Repro: `launch.py --network bridge -- python /results/probe.py`. The runner connected to `api.anthropic.com:443` and to `1.1.1.1:443`.
   - The tools still had none, in both modes: DNS failed, and TCP to `api.anthropic.com`, `1.1.1.1`, and the bridge gateway `172.17.0.1` got "Network is unreachable", because bwrap's `--unshare-net` holds whatever network the container has.
   - So `SPEC.md` Section 3's "tool sandbox has no arbitrary network route" holds. The outer runner, which holds the key, has the same arbitrary egress it has on the host today.
   - Docker has no per-host egress rule. Limiting it would take an internal network plus an allowlisting proxy container, or host firewall rules. **Not built or tested.**

5. **The two loosenings cover the whole container, outer runner included (container).** See the option table. The tools aren't affected: no_exec still fails `execve` (the probe's `exec /bin/sh` got `PermissionError`), and bwrap still mounts only what decision 0023 lists. The added kernel surface reaches the process holding the key during a paid run.

6. **The key file's mode and owner have to suit uid 10001 (container).**
   - A mode-600 file owned by uid 10001, mounted read-only at `/run/secrets/provider.env`: the runner's `load_api_key` read it (35 characters, a fake value).
   - The same file owned by uid 1500: `PermissionError`, which fails closed before any call.
   - A sandboxed tool couldn't see `/run` at all, couldn't read the key or `/run/canary/container.json`, and had no `ANTHROPIC_*` or `OPENAI_*` variable. Its `/proc` showed only PID 1, itself.
   - Never pass the key with `-e`: `docker inspect` shows it, and `environment_refusal` refuses `ANTHROPIC_*` anyway.
   - How Docker Desktop on macOS presents a host file's owner to uid 10001 is **unknown**.

### Breaks the workflow, and fails closed

7. **A read-only checkout blocks `paid_run record` (container).**
   - Where: `runner/paid_run.py:263` writes `protocol/paid_run_record.json` into the checkout.
   - Repro: with `/app` read-only, `OSError: [Errno 30] Read-only file system: '/app/protocol/paid_run_record.json'`.
   - Workaround: `launch.py --writable-protocol` mounts `protocol/` read-write. That also lets the runner write `protocol/development_grid_spec.json`, a hashed path, though a change there would show as a dirty path and refuse.

8. **git refuses a checkout another uid owns (container).**
   - Where: `runner/paid_run.py:69`/`:72` and `runner/mock_slice.py:275` run git with only `PATH` and `LANG`, so no `HOME` and no user config.
   - Repro: mask the image's `/etc/gitconfig` (`-v /dev/null:/etc/gitconfig:ro`) and `code_commit()` returns `None`, and `code_provenance()` returns all-null. The record would refuse "unknown, without git".
   - `Dockerfile.sweep` writes `safe.directory = /app` to `/etc/gitconfig`. With it, git ran on the read-only mount (status with no index write), and the code digest equalled the host's.

9. **buildx's default attestation makes the image ID unreproducible (container).**
   - The image ID Docker reports (`docker container inspect --format {{.Image}}`) is a manifest list. It changed on every build of identical content: `c6bfbca2…`, `9e74524a…`, `95e7b57c…`.
   - With `--provenance=false` it's the platform manifest `f5775dc7…`, which reproduced. `Dockerfile.sweep`'s build notes now say so.

10. **The paid gate opens with an uncommitted record (host too).** In the scratch copy, `git status` showed `?? protocol/paid_run_record.json` and `check` still passed. `protocol/` other than the grid spec isn't hashed. That's outside this brief; it's recorded because it was seen.

11. **The container run is about three times slower.** Mock grid: 57 s vs 18 s on the host. Full suite: 647 s vs 225 s. The cause wasn't measured. Candidates: bwrap and seccomp setup per tool launch, overlayfs, and the read-only bind.

## container_digest: how the prototype sets it

Files: `runner/container.py`, `docker/sweep/launch.py`, `tests/test_container_provenance.py` (6 tests). `runner/mock_slice.py:360`, `runner/paid_run.py:100` and `:198`, and `runner/execute.py:1325` read it.

1. The launcher resolves the image to its ID and creates the container by ID. It asks the daemon which image that container runs, refusing if it differs. It writes `{"container_id", "image_digest", …}` to a host directory mounted read-only at `/run/canary`, and only then starts the container.
2. Inside, `runner/container.py` takes the container ID from the kernel's mount table (the source of Docker's own `/etc/hostname` bind, `/var/lib/docker/containers/<64 hex>/hostname`) and refuses unless the file names that ID and a `sha256:` digest. With no file it returns `None`, which is unknown, never a claim.
3. Results, provenance lines, and the record's preflight carry the value. `run_schedule` checks it before creating the run directory.

Repros (`ba0cc75`, or `d7f5f20` where noted):

- (a) Launcher, same image: record written, `check` passes.
- (b) Launcher, drift image, against the `canary-sweep:proto` grid: `PaidRunRefused: the mock grid ran in image sha256:c6bfbca2… not this one (sha256:01be868f…)` (`d7f5f20`).
- (c) Plain `docker run`, no file: refuses "… not this one (None)".
- (d) A hand-written file naming the good digest, in the drift image: `ContainerMismatch: … written for container ffffffffffff, not this one (6b5b61fa964b)`. `grid_dev mock` refused the same way. At `d7f5f20` it had already left a run directory holding only `runner_mode.json` and `schedule_spec.json`; `ba0cc75` moved the check ahead of the directory.

Residual: an operator who controls the daemon can still forge it, for instance by bind-mounting a fake `/etc/hostname` source path and a matching file. The value is never typed by hand on the supported path, but it isn't proof against its own operator. The CANARY container itself never gets the Docker socket.

## Isolation compared with today's host run under macOS `sandbox-exec`

This comes from reading `tools/sandbox.py`, plus the Linux probes above. **Nothing ran on macOS in this session.**

| Property | Host, macOS `sandbox-exec` (decision 0023, today's plan) | Host, Linux `bwrap` (measured here) | Container, `bwrap` (measured here) |
|---|---|---|---|
| Tool file reads | Profile allow-list. File metadata (`stat`) stays readable everywhere | Only mounted paths exist | Same as Linux host, inside an image that is itself read-only |
| Tool running other programs | Profile allows only the interpreter | no_exec seccomp | Same, and `exec /bin/sh` → `EPERM` |
| Tool network | Only `fixture.sock`, by path | Network namespace with no interfaces | Same, even when the container has a network |
| Tool sees other processes | Profile has no process-info allow; not measured | Own PID namespace | Own PID namespace (PID 1 only) |
| Outer runner (holds the key) | Operator's full account: home, network, everything | Same, as the operator | uid 10001, no capabilities, read-only root and checkout, writes only `/results` and `/tmp`, network `none` by default (any host on `bridge`) |
| Environment pinned | No: Homebrew or python.org Python, the operator's `.venv` | No | Image digest, reproducible on this host. Bound to the record only once the schema says so |
| What had to loosen | Nothing | Ubuntu 23.10+: `kernel.apparmor_restrict_unprivileged_userns=0`, host-wide | Two container options (above) and maybe AppArmor (untested) |

The container adds a boundary around the outer runner that neither host mode has. The tools' boundary is the same as on Linux and about as strict as on macOS: macOS keeps metadata readable everywhere, while bwrap hides unmounted paths. The cost is a wider kernel attack surface inside the container, and an unpinned egress for the runner during paid calls.

## Apple Silicon (arm64, no Docker today)

None of this ran on arm64 or macOS. To try it, the lead's Mac would need to:

1. **Install a Linux VM runtime**: Docker Desktop (or Colima or OrbStack). Its kernel and seccomp support for nested user namespaces are untested here.
2. **Build natively for linux/arm64**: `--platform linux/arm64`, with `--provenance=false`. `tools/no_exec.py` and `tools/sandbox.py` already support aarch64. `docker/sweep/uv-requirements.txt` carries both aarch64 uv wheel hashes. The seccomp `clone` rule reads flags from argument 0, which is right for arm64 too.
   - The result is a **different digest** from `f5775dc7…`. The same source can't give one digest for both platforms, so the record and the paid run must use the arm64 image.
   - An amd64 image under emulation (Rosetta or QEMU) would report `x86_64` to no_exec, but whether a seccomp filter behaves correctly under that translation is **unknown**. I wouldn't use it.
3. **Re-run the ablation** on Docker Desktop. Its VM has no AppArmor that I know of, but **that's unverified**.
4. **Run every paid step in that image**: the mock grid, the record, and the paid commands. The host's `macos-sandbox-exec` fingerprint can never match the container's `linux-bwrap` one (finding 3).
5. **Check the bind mounts**: how the checkout, results, and key file's ownership appear to uid 10001 through Docker Desktop's file sharing (findings 6 to 8).
