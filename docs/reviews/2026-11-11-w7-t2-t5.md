## #73 (`W7-T2`): selection

**No blocking finding.** `select.py` matches `SPEC.md` Section 5 steps 5–8 and decision 0014 on every point below.

| Rule | Result |
|---|---|
| **Eligibility** | Only `status == "evaluation"` rows enter selection. On `main`, 13 are `secret_disclosure` and 14 are `unauthorized_action` (but see N-73-2) |
| **Goal order** | Ascending `SHA256("CANARY-2026\|" + candidate_id)` as lowercase hex, with ties broken by ID |
| **`selection_rank`** | Per goal/family stratum. It is not used for selection |
| **Base order** | Bases alternate goals, disclosure first. At `P` = 20 that gives exactly 10 per goal. Each smaller prefix's split differs by at most one |
| **Caps** | Source cap 10 and family cap 8, checked as each base is placed |
| **Minima** | 3/4/8, 3/4/6, 3/3/4, 2/3/3, and 2/2/3 for 20/15/10/8/6, checked on every prefix of the `P` vector that is built. The high-risk count follows from the index vector, and holds at each size: 8, 6, 4, 3, 3 |
| **Search** | The lexicographically earliest vector of goal positions, with every smaller prefix nested in it |
| **Relaxation** | At each size: the family cap +1, then both caps +1, then the next smaller size. Minima and goal balance are never relaxed |
| **Tasks** | Base *i* gets `INDEX_VECTOR[i-1]`, read through the committed `tasks/task_order.json`, which `tests/test_task_order.py` pins |
| **Recheck sample** | `ceil(0.20 × N)` gives 4/3/2/2/2. Floating point gives `0.2 × 15` as exactly 3.0. The sample is the retained cases with the lowest salted hash over `pool_hash` |
| **`pool_hash`** | Taken over every ledger row's ID, sorted and joined by newlines. It is `864b4614…` at every #73 commit since November 3, so the ID set hasn't changed since before intake closed on November 5 |
| **Determinism** | No randomness, and no order that depends on set iteration |
| **Outcome data** | `select.py` imports only `corpus.intake.selection_hash` and reads only the ledger and `tasks/task_order.json` |

**On `main`'s pool, no rule binds.** The vector is `[1,1,2,2,…,10,10]`: each goal's first ten candidates in goal order. No source or family exceeds 7, and the minima hold at every prefix without the search skipping any candidate. So the real pool exercises none of the cap, minima, or relaxation logic. The synthetic tests and the brute-force comparison above are the only checks of that logic.

### #73: open calls

- **Q-73-1 (how relaxation applies to the nested prefixes).** When a relaxation is used at `P`, `build()` checks every nested prefix against the relaxed caps and reports one relaxation for the whole plan. Example: `P` = 20 under the family cap +1. Its 15-base prefix may hold 9 bases of one family, even if a separate 15-base search would meet the cap of 8. Step 7 and decision 0014 don't say whether a nested prefix must meet the strict caps. Requiring it could change which 20-base vector is earliest. Nothing turns on this today, since `main` needs no relaxation. A ruling is needed before any `W8-T2` freeze that relaxes a cap: keep the behaviour and state it, or check each prefix at its own exact caps first.
- **Q-73-2 (`reviewed_by` approval on #73).** Every `source.reviewed_by` and adapted `reviewed_by` value #73 merged is `marek-sm`, the Section 5 reviewer: 44 and 28 values. The 16 rows rejected at screening, which were never adapted, have `reviewed_by: null`, which `check_ledger` allows. `STATUS.md` and `docs/W7_T2_HANDOFF.md` say the project lead's source review was posted on #73 on November 8. Commit `55cace9`, which `j0hanj` wrote on November 9, put that sign-off into the records. Decision 0031 item 3 also requires the code-owner approval of these record paths to come from the Section 5 reviewer. That approval is on GitHub, and this review made no network call. The project lead confirms that #73's approving review was `marek-sm`'s. If it wasn't, the mismatch is blocking under item 3.
  - **Answered November 11:** `marek-sm` approved #73 on GitHub at 2026-11-11T05:42Z (9:42 pm on November 10, Pacific), clearing the November 7 change request. The approval came from the Section 5 reviewer, so item 3 is met and nothing is blocking.
