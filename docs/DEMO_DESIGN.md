# CANARY Demo Design

This guide controls presentation clarity and accessibility. `SPEC.md` Section 13 owns demo safety and evidentiary meaning. This file does not set a live-demo duration, result, or defense claim.

## Timing status

The live presentation slot is **unconfirmed** until the event organizer provides it. Once confirmed, record in `TASKS.md`:

- the hard slot length;
- the shorter rehearsal target;
- the contingency buffer;
- the date and source of confirmation; and
- which sequence elements are cut first if the slot is shorter than expected.

Do not infer the live slot from the separate two-to-three-minute edited-video requirement.

## Fixed story order

| Sequence | Purpose |
|---:|---|
| 1 | State the trusted task and forbidden external action |
| 2 | Show the fresh synthetic canary and fictional/local safety boundary |
| 3 | Show or run the identical D0_BASELINE case and label request, dispatch, and sink receipt |
| 4 | Show or run D1_POLICY_GATE and distinguish unsafe model proposal from contained tool effect |
| 5 | Show or replay D2_DATAMARKING and describe only what the trace establishes |
| 6 | Label the single case illustrative and show the generated aggregate or `ENGINEERING` validation summary |
| 7 | State one limitation, deliver the scope-matched conclusion, and close |

The order is fixed; timing allocations are not. A lower tier omits absent configurations and gives the recovered space to its actual evidence and limitations.

The Week-13 judge-readiness questions live in `TASKS.md` and point to their canonical answers in `SPEC.md`. They are intentionally not duplicated here because this guide does not own result, metric, or claim semantics.

## Terminal information design

| Region | Required content |
|---|---|
| Header | Active tier, resolved model or `ENGINEERING`, case marked `DEMO / EXCLUDED`, live or recorded state |
| Trusted task | Short task plus allowed/forbidden action summary |
| Untrusted observation | Visually bounded source content with an explicit `UNTRUSTED DATA` label |
| Event timeline | Requested → authorized/blocked → dispatched → effect observed → sink received |
| Outcome | Separate model violation, system compromise, and utility fields |
| Evidence footer | Protocol/trace identifier and `ILLUSTRATIVE — SEE AGGREGATE` label |

## State language

Color supplements words and never replaces them:

- `REQUESTED`
- `AUTHORIZED` or `UNAUTHORIZED`
- `BLOCKED BY POLICY`
- `DISPATCHED TO LOCAL FIXTURE`
- `EFFECT OBSERVED`
- `SINK RECEIVED`
- `NO EVIDENCE / UNKNOWN`
- `RECORDED TRACE`
- `ILLUSTRATIVE — NOT STATISTICAL EVIDENCE`

Do not use “safe,” “secure,” “attack prevented,” or “defense succeeded” as a display shortcut when the stored facts support only a narrower state.

## Accessibility

- Use large readable type and preserve logical reading order.
- Maintain checked contrast and do not rely on red/green distinction.
- Announce state changes in words.
- Avoid rapid flashing, auto-advancing content, and decorative motion.
- Give every chart a text summary and table equivalent.
- Caption the edited video and provide a transcript.
- Test the terminal at the presentation resolution and on a second tested device.

## Safety and reliability

- No audience-supplied task, payload, URL, path, recipient, or arbitrary prompt.
- Use only the excluded demo/development case after protocol freeze.
- Keep one-keystroke replay available and visibly label the transition.
- Switch immediately to replay on provider, authentication, network, or latency failure.
- Replays must be schema-valid and bound to code/configuration hashes.
- A surprising live trace is described honestly and never substituted for aggregate evidence.

## Video

The separate public video is two to three minutes, captioned, transcribed, and offline-capable. It is an edited account, not a claim to reproduce every live step. A full dress-rehearsal recording remains the final audiovisual fallback.
